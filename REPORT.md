## 2. Мета роботи

Спроєктувати та реалізувати узагальнене типобезпечне сховище `Repository<T>`, власну runtime-анотацію `@CsvColumn`, універсальний рефлексивний експортер `CsvExporter`, документний парсер `CsvParser` та спеціалізований виняток `DataStorageException` без використання сторонніх CSV-бібліотек. Інтегрувати підсистему збереження та CSV-експорту у наявний застосунок «Меню кафе» зі збереженням усіх попередніх розрахунків та форматів звіту.

## 3. Проєктування `Repository<T>`

Клас `Repository<T>` реалізує типобезпечне сховище довільних об'єктів у пам'яті:

- **Внутрішній стан та інваріанти:** приватне поле `private final List<T> items = new ArrayList<>();` приховує внутрішню колекцію. Метод `add(T item)` перевіряє елемент через `Objects.requireNonNull` і не допускає `null`.
- **Незмінний знімок (`all()`):** повертає `List.copyOf(items)`, тому зовнішній код не може змінити стан сховища через повернений список (`UnsupportedOperationException` при спробі модифікації).
- **Контраваріантний пошук (`find(Predicate<? super T>)`):** використання wildcard-обмеження `? super T` (принцип PECS — _Consumer Super_) дозволяє передавати предикати, визначені як для самого типу `T` (наприклад, `Predicate<MenuItemRecord>`), так і для будь-якого його супертипу (наприклад, `Predicate<Object>`).
- **Обмеження generics у Java:** через стирання типів (_type erasure_) на етапі виконання параметр `T` замінюється на `Object`, тому всередині класу неможливо виконати `new T()`, `new T[]` або `instanceof T` без явної передачі `Class<T>`.

## 4. Механізм `@CsvColumn` і рефлексія

- **Оголошення анотації:**
  ```java
  @Retention(RetentionPolicy.RUNTIME)
  @Target(ElementType.FIELD)
  public @interface CsvColumn {
      String value();
  }
  ```
  `RetentionPolicy.RUNTIME` зберігає метадані у `.class`-файлі та робить їх доступними під час виконання через Reflection API, а `ElementType.FIELD` обмежує застосування анотації виключно полями класу.
- **Алгоритм `CsvExporter.write(Path, Class<T>, List<? extends T>)`:**
  1. Проходить ієрархію класів від `type` до `Object` (не включно), збираючи всі оголошені поля (`getDeclaredFields()`), позначені `@CsvColumn`.
  2. Сортує знайдені поля за алфавітом їхніх імен (`Comparator.comparing(Field::getName)`), що гарантує детермінований порядок стовпців незалежно від порядку повернення полів у JVM.
  3. Відкриває доступ до `private`-полів через `field.trySetAccessible()`, зчитує значення `field.get(record)` та перехоплює `IllegalAccessException` із обгортанням у `DataStorageException`.
  4. Експортує будь-який плоский клас з анотованими полями без прив'язки до конкретного типу моделі (підтверджено тестом на сторонньому класі `SampleDto`).

## 5. Формат CSV, правила екранування та парсингу

- **Кодування та структура:** файл записується у кодуванні `StandardCharsets.UTF_8` (без BOM), роздільник полів — кома (`,`), перенесення рядків — `System.lineSeparator()`. Перший рядок містить заголовки, задані в `@CsvColumn.value()`.
- **Правила екранування (`CsvExporter.escape`):**
  - Якщо текстове представлення значення містить кому (`,`), подвійні лапки (`"`), символ `\r` або `\n`, воно береться в подвійні лапки `"..."`.
  - Усі внутрішні подвійні лапки подвоюються (`"` -> `""`).
  - Значення без спецсимволів записуються без зайвих лапок.
- **Документний парсер (`CsvParser.parseDocument`):**
  - Замість наївного `String.split(",")` реалізовано скінченний автомат (state machine), який відстежує стани `quoted` та `quoteClosed` посимвольно.
  - Це дає змогу коректно розбирати поля з комами, екранованими подвійними лапками `""` та багаторядковими перенесеннями `\n` / `\r\n` усередині лапок як один логічний запис.

## 6. Приклад вхідних даних та згенерованого CSV

Під час виконання контрольного запуску на вхідному файлі `data/input.csv` у `target/menu-export.csv` формується такий документ (UTF-8):

```csv
категорія,назва,час готування,ціна,вага
DRINK,Капучино,5,50.5,250
DESSERT,Сирник домашній,10,71.5,180
DISH,Борщ український,20,109.24999999999999,350
```

_(Примітка: значення `109.24999999999999` є точним поданням `95.0 * 1.15` у стандарті IEEE 754 `double`, що гарантує побітове відновлення ціни під час зворотного парсингу без втрати точності округлення)._

**Приклад екранування спецсимволів (із round-trip тесту на 5 записах):**

```csv
категорія,назва,час готування,ціна,вага

DRINK,"Кава ""Еспресо"" подвійна",3,55.0,60
DRINK,"Чай трав'яний
з м'ятою та медом",5,60.0,300
DESSERT,Сирники зі сметаною,15,95.0,220
DISH,Вареники з картоплею,12,88.0,300
```

## 7. Обробка помилок

Усі помилки формату CSV, валідації записів, доступу через рефлексію та операцій введення/виведення інкапсулюються у власному винятку `DataStorageException` зі збереженням першопричини (`cause`):

| Ситуація / помилковий сценарій                        | Клас і метод                        | Тип винятку та збережена причина (`getCause()`)                      |
| :---------------------------------------------------- | :---------------------------------- | :------------------------------------------------------------------- |
| Клас не містить жодного поля з `@CsvColumn`           | `CsvExporter.write`                 | `DataStorageException` (`cause == null`)                             |
| Список для експорту містить `null`-елемент            | `CsvExporter.write`                 | `DataStorageException` (`cause == null`)                             |
| Помилка запису файлу (наприклад, шлях є каталогом)    | `CsvExporter.write`                 | `DataStorageException` (`cause instanceof IOException`)              |
| Незакриті подвійні лапки або символи після лапок      | `CsvParser.parseDocument`           | `DataStorageException` (`cause == null`)                             |
| Порожній рядок або кілька записів у `parse(line)`     | `CsvParser.parse`                   | `DataStorageException` (`cause == null`)                             |
| Кількість полів CSV не дорівнює 5                     | `MenuItemRecord.fromFields`         | `DataStorageException` (`cause == null`)                             |
| Невідоме значення категорії `MenuKind`                | `MenuItemRecord.fromFields`         | `DataStorageException` (`cause instanceof IllegalArgumentException`) |
| Некоректне число для ціни, ваги або часу приготування | `MenuItemRecord.fromFields`         | `DataStorageException` (`cause instanceof NumberFormatException`)    |
| Передача `null` у `Repository.add` або `find`         | `Repository.add`, `Repository.find` | `NullPointerException`                                               |

## 12. Самооцінка якості

- **Дотримання SRP та незмінності:** кожен новий клас виконує одну чітку роль (`Repository` — зберігання, `CsvExporter` — рефлексивна серіалізація, `CsvParser` — лексичний розбір CSV, `MenuItemRecord` — незмінний DTO-запис).
- **Детермінованість:** сортування анотованих полів за іменем гарантує однаковий порядок стовпців на будь-якій версії JDK, а явне використання `StandardCharsets.UTF_8` усуває залежність від локалі ОС.
- **Чистий репозиторій:** вихідний файл `target/menu-export.csv` генерується у каталог збірки `target/`, який виключено з індексації Git.

## 13. Трудність і найбільш крихке місце

Найбільш чутливим місцем під час реалізації стало узгодження **багаторядкового CSV-експорту** та **порядку полів при зворотному відновленні (round-trip)**:

1. Якби парсер читав файл через `Files.readAllLines()` і розбивав кожен рядок окремо, значення з символом перенесення рядка `\n` усередині лапок (наприклад, `"Чай трав'яний\nз м'ятою та медом"`) розірвалося б на два пошкоджені рядки. Проблему розв'язано переходом на посимвольний документний скінченний автомат `CsvParser.parseDocument(String)`.
2. Оскільки `Class.getDeclaredFields()` не гарантує фіксованого порядку полів у специфікації JVM, у `CsvExporter` запроваджено сортування `Comparator.comparing(Field::getName)`, що детерміновано формує порядок `category, name, preparationMinutes, price, weightGrams` (`категорія,назва,час готування,ціна,вага`), узгоджений із `MenuItemRecord.fromFields`.

## 15. Відповіді на контрольні питання

1. **Для чого потрібні узагальнені типи (generics) у Java?** Вони забезпечують типізацію на етапі компіляції, усувають необхідність явного приведення типів і дозволяють створювати повторно використовувані алгоритми та контейнери без втрати типобезпеки.
2. **Що таке стирання типів (type erasure) і які обмеження воно накладає?** Під час компіляції інформація про параметри типу стирається (замінюється на `Object` або верхню межу `T extends ...`), тому в runtime неможливо створити `new T()`, створити масив `new T[10]` або виконати `obj instanceof T`.
3. **У чому різниця між `Repository<MenuItem>` і `Repository<Object>`?** У Java generics є інваріантними: `Repository<MenuItem>` не є підтипом `Repository<Object>`, хоча `MenuItem` є підтипом `Object`.
4. **Коли застосовують `? extends T`, а коли `? super T` (принцип PECS)?** _Producer Extends, Consumer Super_: `? extends T` використовують, коли колекція лише постачає об'єкти типу `T` для читання, а `? super T` — коли об'єкт типу `T` передається у споживач (наприклад, `Predicate<? super T>` або запис у колекцію).
5. **Чим `Class<T>` відрізняється від екземпляра класу `T`?** Екземпляр `T` представляє конкретний об'єкт даних у пам'яті, тоді як `Class<T>` є метаоб'єктом JVM, що описує структуру самого типу (його поля, методи, конструктори та анотації).
6. **Чим `getDeclaredFields()` відрізняється від `getFields()`?** `getFields()` повертає лише `public`-поля класу та всіх його суперкласів, тоді як `getDeclaredFields()` повертає всі поля (включно з `private`, `protected` та package-private), оголошені безпосередньо в поточному класі.
7. **Навіщо в рефлексії викликають `setAccessible(true)` або `trySetAccessible()` і які ризики це несе?** Це дає змогу читати або змінювати `private`-поля об'єкта. Ризики: порушення інкапсуляції та можлива відмова (`InaccessibleObjectException` або `false` від `trySetAccessible()`) у модульних пакетах Java 9+, якщо пакет не відкрито (`opens`).
8. **Яке призначення метаанотацій `@Retention` і `@Target`?** `@Retention` визначає життєвий цикл анотації (`SOURCE`, `CLASS` або `RUNTIME` — чи буде вона доступна через рефлексію під час роботи програми), а `@Target` вказує, до яких елементів коду її можна застосовувати (поля, методи, класи тощо).
9. **Як перевірити наявність анотації на полі та прочитати її атрибут у runtime?** Викликати `field.isAnnotationPresent(CsvColumn.class)`, а потім отримати екземпляр анотації через `CsvColumn col = field.getAnnotation(CsvColumn.class)` і прочитати `col.value()`.
10. **Чим `java.nio.file.Path` і `Files` кращі за застарілий `java.io.File`?** `Path` і `Files` підтримують сучасну обробку винятків (`IOException` замість мовчазного повернення `false`), явне вказання кодування (`StandardCharsets.UTF_8`), потокові операції, символічні посилання та кращу кросплатформність.
11. **Чому під час читання та запису текстових файлів потрібно явно вказувати `StandardCharsets.UTF_8`?** Без явного кодування методи використовують кодування середовища за замовчуванням, що може призвести до спотворення кирилиці («кракозябрів») під час перенесення програми між Windows, Linux та macOS.
12. **Що таке BOM (Byte Order Mark) у UTF-8 і коли він заважає?** Це службова послідовність байтів `EF BB BF` на початку файлу. У Java вона не потрібна для UTF-8 і під час читання потрапляє як символ `\uFEFF` до першого поля першого рядка, ламаючи порівняння рядків або `Enum.valueOf()`.
13. **Як у CSV екрануються кома, подвійні лапки та перенесення рядка?** Усе поле береться у подвійні лапки `"..."`, а кожні подвійні лапки всередині тексту замінюються парою подвійних лапок `""`.
14. **Чому наївний розбір CSV через `line.split(",")` не підходить для реальних даних?** Він не розрізняє кому-роздільник стовпців і кому всередині взятого в лапки текстового значення, а також не здатний обробити перенесення рядка всередині лапок.
15. **Як забезпечити фіксований порядок стовпців під час рефлексивного експорту в CSV?** Відсортувати масив/список `Field` за критерієм детермінованого порядку (наприклад, за іменем поля `Field::getName` або за явним порядковим параметром в анотації).
16. **Чим власний виняток корисніший за загальний `Exception` або `RuntimeException`?** Власний виняток (`DataStorageException`) чітко відділяє помилки рівня зберігання та парсингу даних від інших збоїв програми й дозволяє викликаючому коду обробляти їх спеціалізовано.
17. **Навіщо передавати першопричину (`cause`) у конструктор винятку?** Це зберігає повний стек викликів (`stack trace`) початкового системного збою (наприклад, `IOException` або `NumberFormatException`), що критично для діагностики причин помилки.
18. **У чому різниця між `checked` і `unchecked` винятками під час проєктування API?** `Checked`-винятки (нащадки `Exception`) зобов'язують викликаючий код явно обробити або прокинути очікувану зовнішню помилку (наприклад, збій файлової системи), тоді як `unchecked` (`RuntimeException`) сигналізують про порушення контракту виклику (наприклад, `null`-аргумент).
19. **Що таке перевірка `round-trip` і що саме вона доводить?** Це цикл перетворення даних «об'єкт → зовнішній формат (CSV) → відновлений об'єкт» із перевіркою `original.equals(restored)`. Вона доводить, що під час серіалізації та парсингу не втрачаються дані, типи й спецсимволи.
20. **Які переваги дає JUnit-анотація `@TempDir` у тестах файлового введення/виведення?** Вона автоматично створює ізольований тимчасовий каталог для кожного тесту та гарантовано видаляє всі створені в ньому файли після завершення тесту, не засмічуючи проєкт.
